# Shared application and platform integration

The portable application is `dist/app`. The browser, an installable PWA, and future mobile/desktop WebView shells can use the same folder. It contains the C++ engine compiled to WebAssembly, the existing JavaScript/SVG editor, fonts, handbook, and installation assets. Python and a native simulation service are not required at runtime.

## Shared code

| Layer | Location | Responsibility |
| --- | --- | --- |
| Engine | `src/engine/` | Components, primitive evaluation, memory, lessons, and checking |
| Engine access | `src/ui/engine/` | Worker lifecycle and typed C-ABI calls |
| Application | `src/ui/app.js` and editor modules | Editing, rendering, routing, layout, lesson navigation, and shared import validation |
| Device capabilities | `src/ui/platform.mjs` | Persistence access, file selection/export, suspension, and offline setup |
| Native shell | Future `platforms/<shell>/` projects | OS integrations, lifecycle forwarding, signing, and distribution |

`src/ui/` is the editable shared source; `dist/app/` is generated by `scripts/build_app.py` and excluded from Git. The same bundle is consumed by every host. `deploy/` contains web hosting configuration. Create `platforms/` when the native shell is selected, with only its project files and platform integrations; keep shared UI code in `src/ui/`.

The UI submits `catalog`, `reference`, `simulate`, and `check` requests through one Promise-based interface. It does not choose an engine according to the operating system. All three application types can use the same WebAssembly worker. The native C++ API and optional HTTP service remain available for other integrations.

## Current platform adapter

`platform.mjs` exports one object with the capabilities the editor actually uses:

- `readText(key)` and `writeText(key, value)` use local storage. JSON formats and migration rules remain in the shared application.
- `exportFile(name, contents)` shares a JSON file on touch devices when file sharing is supported; otherwise it downloads the file. It resolves to false when the user cancels a share.
- `bindFileImport(onFile)` returns the action for the import button and delivers a browser `File` to shared validation. A native picker can deliver a `File` constructed from its returned bytes.
- `onSuspend(save)` flushes pending saves on page hide, unload, and backgrounding. A native shell should also forward its suspension event.
- `prepareOffline()` registers the web service worker. A shell with bundled assets can replace it with a no-op.

A shell entry module can import this object, replace the capabilities it needs, and then import `app.js`. Load that entry instead of `app.js` in the shell's HTML. Keep native integrations outside the shared editor; do not scatter OS checks through event handlers or circuit code. There is no platform framework or plugin registry to maintain.

The current storage interface is synchronous because all proposed WebView shells provide local storage. A future asynchronous storage plugin would require an explicit startup/read cache; do not make an asynchronous native call look synchronous. Local storage and export/import are sufficient for the current application.

## Mobile and desktop packaging

The shell is still a choice; none is included yet. These options all preserve the shared C++/WebAssembly engine and web editor:

| Option | Targets | Main tradeoff |
| --- | --- | --- |
| Installable PWA | Browsers on mobile and desktop, where installation is supported | Already implemented; browser installation, storage, and OS integration vary |
| Tauri 2 | Android, iOS, Windows, macOS, Linux | One shell framework; introduces Rust tooling and requires testing each platform's system WebView |
| Capacitor + Tauri | Capacitor for Android/iOS; Tauri for desktop | Mobile-focused native plugins, with two shell/build setups around the same web bundle |
| Capacitor + Electron | Capacitor for Android/iOS; Electron for desktop | Electron provides a consistent desktop Chromium runtime, with a larger download and memory footprint |

Capacitor can set `webDir` to `dist/app`; Tauri and Electron can bundle that same output. A wrapper does not itself accelerate the SVG editor. Measure panning, wiring, and active-wire animation on target devices before choosing a different renderer or adding a native C++ bridge. For any packaged option:

1. Build the web bundle and copy it as an application asset.
2. Serve assets through the shell's supported local origin/protocol, with JavaScript module and WebAssembly MIME types. Do not rely on opening `index.html` with `file://`.
3. Allow local module workers and WebAssembly in the shell's content policy. The engine uses no shared memory, native Node access, or network API.
4. Connect native file pickers/sharing and lifecycle events through the platform adapter as needed.
5. Test the real WebView on supported devices: installation, background/resume, cold start, memory circuits, pinch zoom, wiring, file cancellation, and persistence across app upgrades.

CSS responsive layouts and pointer events remain shared. Different layouts and hit-target sizes should follow screen size and input capability. Mobile usability still needs real-device work; emulated viewports do not reproduce finger accuracy, WebView differences, battery use, or app lifecycle behavior.

## Suggested next step, pending a platform decision

Keep the first package small: one mobile target and one desktop target, using the same WebAssembly worker. A Tauri 2 proof of concept would test the single-shell approach before committing to it. Confirm local asset/worker loading, pinch/pan/wiring, import/export, background/resume, and saves across an application upgrade. Use actual devices as well as emulators. iOS and macOS packaging/signing require macOS tooling; plan build runners for each desktop target.

Then add the integrations the trial demonstrates a need for: file dialogs and sharing, safe-area handling, the mobile back action, lifecycle save hooks, and platform update packaging. Keep these in the shell adapter. Existing editor modules should be split further only when their responsibilities demand it; a new framework or duplicate UI is not required for packaging.

Before a broader release, make web updates visible to players and offer whole-progress backup/restore. The current export transfers individual circuits, while a browser origin and a native application have separate progress storage.

## Persistence and updates

Existing `signal-garden-v2` storage keys, version-2 circuit files, and stable lesson IDs are preserved. Version-1 migration still leaves original saves intact. Clocked memory intentionally initializes to zero when reopening a workspace, matching previous behavior.

A browser, PWA, and native app may use different storage origins. Installing a native app does not automatically migrate a browser's progress. Circuits can be moved with existing JSON export/import; whole-progress transfer or account synchronization is separate work.

The web build caches all required files under one content version. It activates updates after existing app tabs/windows close, so an open application keeps its engine and interface together. Native application stores can replace the packaged bundle as one application update and disable service-worker caching.

## Delivered scope

The WebAssembly worker, static build, offline cache, installation manifest/icons, and capability boundary are implemented. The C++ engine and web editor remain shared. Native Android/iOS projects, desktop installers, signing, store submission, and physical-device validation are subsequent steps.
